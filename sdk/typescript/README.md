# worldview-core (TypeScript)

TypeScript SDK for the [worldview-core](../../README.md) format: a portable JSON
representation of a **worldview**, a set of natural-language **statements** connected by
**arguments**, where an argument is a directed hyperedge from N premise statements to M
conclusion statements.

This package is a complete port of the Python reference implementation: validation,
content-derived identity hashing, structural queries, argument planning, lints,
statistics, Markdown presentation, DOT and Mermaid export, diff, three-way merge, the
JSON Schema, and a CLI.
It has **zero runtime dependencies**, is **synchronous** throughout, and runs unchanged in
**Node and browsers** (SHA-256 is implemented in pure TypeScript; the only Node-specific
code is the CLI).

**Hashes and outputs are identical to the Python implementation.** Every `prop_id`,
`just_id`, `arg_hash`, every query, plan, lint, statistic, diff, and merge result is
byte-for-byte the same as `worldview_core` produces, and the text outputs (`present`,
`toDot`, `toMermaid`) are the same text character for character. The repository's
conformance suite (`conformance/vectors/`, generated by `conformance/generate.py` from the
Python code) is replayed in full by `npm test`: primitives (`canon` and `H` pairs), every
case file (identities, foundations, sccs, well-founded lint, and `rests_on` / `supports`
at full depth and depth 1 for every statement), every invalid document, every diff, every
extras file (`plan` with several given sets, `lint_all`, `stats`, `present` plain / at
depth 1 / with given statements, and the DOT and Mermaid exports with two option sets),
and every three-way merge, all compared with deep equality or, for text, exact equality.

## Install

```
npm install worldview-core
```

Requires Node 18 or newer for the CLI and tests; the library itself needs only ES2022,
`TextEncoder`, and `String.prototype.normalize`.

From this repository:

```
cd sdk/typescript
npm install
npm run build      # -> dist/ (ESM + .d.ts)
npm test           # builds, then replays the conformance vectors and unit tests
```

## API

Everything is exported from the package root. Names are camelCase versions of the Python
API; result objects keep the Python key names (`prop_id`, `co_conclusions`, ...) so the
JSON is interchangeable.

### Parsing and validation

```ts
import { parseWorldview, parseWorldviewJson, validateDict, ValidationError } from "worldview-core";

const wv = parseWorldviewJson(text, "my-worldview.json"); // throws LoadError / ValidationError
const wv2 = parseWorldview(JSON.parse(text));             // same, from parsed data

const problems = validateDict(raw); // string[]; empty means valid
try {
  parseWorldview(raw);
} catch (e) {
  if (e instanceof ValidationError) console.log(e.problems);
}
```

- `validateDict(data: unknown): string[]` mirrors the Python validator: structural checks
  that match the JSON Schema exactly plus referential integrity (unique ids, every
  reference resolves). Cycles are never a problem.
- `parseWorldview(data: unknown, source?: string): Worldview` validates and builds.
- `parseWorldviewJson(text: string, source?: string): Worldview` also parses JSON text.
- `worldviewFromDict(doc, source?)` builds without validating; `worldviewToDict(wv)` gives
  back the file form (round-trips exactly). `meta` and `ext` are carried through untouched.
- `getStatement(wv, id)`, `getArgument(wv, id)` (throw `UnknownIdError`), `statementIds(wv)`,
  `argumentIds(wv)`.

`Worldview`, `Statement`, and `Argument` are plain object types mirroring the JSON:

```ts
interface Statement { id: string; text: string; mode: "is" | "ought"; meta?: JsonObject; ext?: JsonObject }
interface Argument  { id: string; premises: string[]; conclusions: string[]; justification: string;
                      rule?: string; meta?: JsonObject; ext?: JsonObject }
interface Worldview { version: string; name?: string; description?: string; meta?: JsonObject; ext?: JsonObject;
                      statements: Statement[]; arguments: Argument[]; source?: string }
```

### Identity

```ts
import { computeIdentities } from "worldview-core";

const ids = computeIdentities(wv);
ids.propId.get("walk-commute");   // 64-hex proposition id
ids.justId.get("walk-commute");   // 64-hex justified-statement id
ids.argHash.get("walk-for-health");
ids.sccOf("habit-reports");       // ["self-knowledge", "habit-reports"] or null
ids.toDict();                     // { statements: [{ id, prop_id, just_id, scc? }], arguments: [{ id, arg_hash }] }
```

The primitives are exported too: `canon(text)`, `H(...parts)` (each part a string or a
string array), `propId(text, mode)`, `WHITESPACE`, and `sha256Hex(bytesOrString)`.

### Queries

Each returns plain data, identical in shape and order to the Python functions and to the
CLI's `--json` output.

```ts
import { foundations, sccs, restsOn, supports, wellFounded } from "worldview-core";

foundations(wv);                     // [{ id, text, mode }]
sccs(wv);                            // [{ members, self_loops, internal_arguments, boundary_arguments }]
restsOn(wv, "need-raincoat");        // { statement, text, direction: "up", closure, sccs, tree }
restsOn(wv, "need-raincoat", 2);     // depth limit: cut-off nodes carry truncated: true
supports(wv, "walk-commute");        // direction "down": co_premises + conclusions per argument
wellFounded(wv);                     // { foundations, grounded, ungrounded }
```

In a closure `tree`, each statement is expanded once; a later encounter is a leaf with
`seen: true`. Nodes inside a cycle carry `scc: [...]`. Unknown ids throw `UnknownIdError`.

### Planning, lints, statistics

```ts
import { plan, duplicates, unused, emptyJustifications, isOughtGaps, lintAll, stats } from "worldview-core";

plan(wv, "need-raincoat", ["walk-commute"]);
// { statement, text, given, must_establish: [{ id, text, via }], must_grant: [{ id, text }],
//   arguments, sccs, tree }   -- the rests-on tree pruned at given statements (leaves given: true)

duplicates(wv);          // [{ prop_id, text, mode, ids }]: the same proposition under several ids
unused(wv);              // statement ids in no argument
emptyJustifications(wv); // argument ids whose justification canonicalizes to ""
isOughtGaps(wv);         // [{ argument, ought_conclusions, premises }]: an ought concluded from is premises alone
lintAll(wv);             // { well_founded, duplicates, unused, empty_justifications, is_ought_gaps }
stats(wv);               // counts, cycle sizes, premises/conclusions { min, max, mean }, longest_chain, top lists
```

`stats().premises.mean` is rounded exactly as Python's `round(x, 3)` (ties to even on the
exact binary value; `pyRound` is exported for the curious).

### Presentation and export

```ts
import { present, toDot, toMermaid } from "worldview-core";

present(wv, "need-raincoat");                            // Markdown: the whole case, foundations up
present(wv, "need-raincoat", { given: ["walk-commute"] }); // pruned at given statements
present(wv, "need-raincoat", { depth: 1 });              // depth limit (ignored when given is non-empty)
toDot(wv, { ids: true, wrap: 36, rankdir: "LR" });       // Graphviz DOT source
toMermaid(wv, { ids: true, wrap: 36, direction: "LR" }); // Mermaid flowchart source
```

All three return exactly the text the Python functions return. Label wrapping in the
exports is a faithful port of Python's `textwrap.wrap` (greedy fill in code points,
breaks on whitespace and after hyphens, breaks long words), exported as `textwrap(text,
width)`. A non-positive `wrap` throws `RangeError`, where Python raises `ValueError`.

### Merge

```ts
import { merge } from "worldview-core";

const m = merge(base, ours, theirs);
m.merged;     // the merged document (file form): base order, then additions from ours, then theirs
m.conflicts;  // [{ kind: "statement" | "argument" | "header", id, base, ours, theirs, resolution },
              //  { kind: "dangling", id, missing, argument, resolution: "dropped argument" }]
m.summary;    // { statements: { kept, changed, added_ours, added_theirs, added_both, removed }, arguments: {...} }
```

Entries are matched by local id and compared by content (statements: canonical text,
mode, `meta`, `ext`; arguments: premise set, conclusion set, canonical justification,
`rule`, `meta`, `ext`). `meta` / `ext` are compared with Python's equality semantics so the
result matches the reference implementation (object key order is irrelevant, array order
is not, `true == 1`).

### Diff

```ts
import { diff } from "worldview-core";

const d = diff(a, b);
d.statements.identical;    // [{ a, b, just_id }]
d.statements.rejustified;  // [{ a, b, prop_id, text }]
d.statements.added;        // [{ id, text, mode }]  (in b only)
d.statements.removed;      // (in a only)
d.arguments.identical;     // [{ a, b, arg_hash }], plus added / removed
d.summary;                 // counts
```

### Graph

`Graph.build(wv)` exposes `incoming` / `outgoing` (statement id to argument ids),
`succ` / `pred` (statement adjacency), `foundations()`, `sccs()` (topological order, same
member order as Python), `sccOf()`, `isCyclicComponent(comp)`, `cyclicSccs()`,
`upstream(id, stop?)`, `downstream(id, stop?)` (`stop` is a set of ids the walk reaches but
does not continue past). Every query accepts an optional pre-built `Graph` as its last
argument.

### Schema

```ts
import { schema } from "worldview-core"; // the JSON Schema (draft 2020-12) as a plain object
```

Identical in content to `src/worldview_core/worldview-core.schema.json`; regenerate with
`npm run sync-schema` if the schema changes.

## Command line

`bin/worldview.js` mirrors the Python CLI. After `npm install -g worldview-core` (or from
this directory, `node bin/worldview.js` after building):

```
worldview [--json] <command> ...

  validate <file> [--jsonschema]
  ids <file>
  rests-on <file> <id> [--depth N]
  supports <file> <id> [--depth N]
  foundations <file>
  sccs <file>
  plan <file> <id> [--given a,b,...]
  lint well-founded | duplicates | unused | empty-justifications | is-ought | all <file>
  present <file> <id> [--given a,b,...] [--depth N] [-o FILE]
  stats <file>
  diff <a> <b>
  merge <base> <ours> <theirs> [-o FILE] [--force]
  export <file> [--format dot|mermaid] [--no-ids] [--wrap N] [--direction LR|TB|RL|BT] [-o FILE]
  schema
```

`--json` emits exactly the data the library returns (the same as the Python CLI's `--json`;
`present --json` wraps the Markdown as `{"statement", "markdown"}`; `export` and `present`
without `--json` write their text). `merge` exits 1 when there are conflicts and writes
`-o` only when conflict-free or with `--force`. Exit codes: 0 success, 1 the file is not
a valid worldview (or cannot be read), 2 usage error or unknown id. `--jsonschema` is
accepted for parity with the Python CLI but only prints a warning: the built-in validator
already mirrors the schema exactly, and this package has no JSON Schema dependency.

The argparse conventions of the Python CLI hold here too: a long option may be shortened
to any unique prefix (`--giv` for `--given`), `--depth` and `--wrap` take whatever Python's
`int()` takes, and `--` ends option processing so that a statement whose id starts with
`-` can be named (`worldview plan file.json --given=a -- -x`). Beyond the Python CLI,
`--json` is also accepted after the command name, and an id that starts with `-` is
accepted as a positional argument or option value without `--`.

```
$ worldview rests-on examples/walking-to-work.json need-raincoat
need-raincoat: I should own a good raincoat.
  <- raincoat
      walk-commute: I should walk to work.
        <- walk-for-health [practical syllogism]
            exercise-good: Regular physical activity improves long-term health.  [foundation]
            ...
```

## Development

```
npm run build       # tsc -> dist/
npm run typecheck   # type-check src and tests without emitting
npm test            # build + vitest (conformance replay, SHA-256, API, CLI)
npm run clean       # remove dist/
npm run sync-schema # regenerate src/schema.ts from the Python package's schema
npm run fuzz        # cross-language fuzz against the Python reference (needs the repo's .venv)
```

Layout mirrors the Python modules: `src/canon.ts`, `src/sha256.ts`, `src/model.ts`,
`src/validate.ts`, `src/graph.ts`, `src/identity.ts`, `src/queries.ts`, `src/lint.ts`,
`src/stats.ts`, `src/present.ts`, `src/export.ts`, `src/merge.ts`, `src/diff.ts`,
`src/schema.ts`, `src/cli.ts`, `src/index.ts`; `src/textwrap.ts` and `src/pyfloat.ts` hold
the two pieces of Python behaviour (`textwrap.wrap`, `round`) the text outputs depend on.

### Fuzzing against the Python reference

`npm test` is self-contained (it replays the checked-in conformance vectors). `npm run
fuzz` goes further: `scripts/fuzz.mjs` generates random worldviews of many shapes (dense
cycles, self-loops, zero-premise arguments, joint conclusions, unicode text in every
normalization form, ids such as `__proto__`, nested `meta`/`ext`), runs each through this
SDK and through the Python implementation (`scripts/fuzz-reference.py`, on the repository's
`.venv`), and compares with deep equality: validity, every hash, the full SCC order,
foundations, sccs, the well-founded lint, `rests_on`/`supports` for every statement at
several depths, diffs in both directions against a mutated copy, `plan` for several
targets with random given sets, `lint_all`, `stats`, `present` (plain, with a depth, with
given statements) as exact text, the DOT and Mermaid exports with random options as exact
text, and the three-way merge of the worldview with three mutated variants. A hand-built
corpus of edge shapes runs first, random text and part lists go through `canon`/`H`, random
text and widths through `textwrap`, corrupted documents through both validators, and on a
sample of graphs the two CLIs' stdout is compared byte for byte for every command.
`--count`, `--seed`, `--cli`, `--python`, and `--out` (where failing inputs are written)
are documented at the top of the script.

Two known, deliberate non-goals of the comparison: Python's hand-written validator accepts
an `id` or `version` with a trailing newline (its `$` anchor matches before a final `\n`),
which the JSON Schema and this SDK reject; and NFC of characters assigned after the Unicode
version that the local Python was built with (15.1 for Python 3.13, against 17.0 in Node
24) can differ in canonical reordering. The fuzzer avoids both.

Two more differences are inherent to JSON in JavaScript and only visible when a command
echoes `meta` / `ext` (`merge`): a number written as `1.0` in a file prints as `1` here
and `1.0` in Python, and an object key that looks like an integer (`"0"`) is ordered first
by JavaScript. Neither affects hashes, queries, or which entries a merge chooses.
